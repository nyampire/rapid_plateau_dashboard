# 設計: 取り込み率が90%以上の都市も完了に数える

作成日: 2026-10-20

## 解く問題

ダッシュボードの完了都市数は、OSM wikiの`JA:MLIT_PLATEAU/imports_list`で完了と記載された都市だけを数えています。
取り込みが終わっていてもwikiに書かれていない都市は、完了に数えられません。

たとえば東京都の西東京市、武蔵野市、三鷹市、調布市、東久留米市は、2026年8月から10月に1人の利用者がPLATEAUの建物を取り込み、取り込み率は97%から99%です。
5市ともwikiには節がなく、ダッシュボードでは「未着手」と出ています。

今の画面は、率が90%以上の都市を「ほぼ完了」として別に出しています。
2026-10-18の集計では、wikiの完了が33都市、率90%以上が60都市で、30都市が両方に入っています。

## 決めたこと

完了の定義を次のように改めます。

- wikiで完了と記載された都市は、取り込み率に関係なく完了です。
- wikiに記載がなくても、取り込み率が90%以上の都市は完了です。
- 完了の都市数は、この2つのどちらかに当てはまる都市の数です。

2026-10-18の数字では、33＋30＝63都市になります。
wikiで完了なのに率が90%に届かない新座市（89.96%）、東村山市（82.87%）、玉名市（80.7%）も完了に含みます。

率は週次の集計で変わります。
wikiに記載のない都市は、率が90%を割った週から完了に数えません。

この変更は、`docs/DESIGN.md`の3.3節と9節で決めた「完了はwikiの完了日を正式な基準にし、率は補助にする」という取り決めを改めるものです。
wikiの読み込みと、都市ごとのwikiの状態（`osm_import_status`）は今のまま残します。

## 目標と、目標にしないこと

目標は、画面、API、週次の記録のどこで見ても、完了の数が同じ定義で数えられていることです。

目標にしないことは次のとおりです。

- 90%という境目を見直すこと。
- 過去の週の完了の数を、新しい定義で数え直すこと。
  過去の週の都市ごとの率は残っていないので、数え直せません。
- wikiへの記載を自動で促すこと。

完了の数が画面とAPIで食い違うことは、失敗とみなします。
過去の記録のwikiの完了の数が、ある週から別の意味に変わることも失敗とみなします。

## API（`api/dashboard_api.py`）

数の名前は、どの応答でも次の2つにそろえます。

| 名前 | 意味 |
|---|---|
| `cities_done` | 新しい定義の完了の都市数（wikiの完了か、率90%以上） |
| `cities_osm_done` | wikiで完了の都市数（今と同じ意味） |

応答ごとの変更は次のとおりです。

- `/summary`：`cities_done`を足します。
  `cities_osm_done`は今の意味のまま残します。
  境目の値`rate_done_threshold`（90）も返し、画面はこの値を使います。
- `/regions`：今の`cities_done`はwikiの完了の数ですが、これを新しい定義の数に変えます。
  wikiの完了の数は、新しく`cities_osm_done`として返します。
- `/progress`：`cities_done`を週次の記録から返します。
  記録が空の週は`null`です。
- `/cities`と`/cities/{code}`：都市ごとに`done_source`を足します。
  値は、wikiで完了なら`"wiki"`、wikiでは完了でなく率が90%以上なら`"rate"`、どちらでもなければ`null`です。
  両方に当てはまる都市は`"wiki"`です。

率は`dash_city_stats.import_rate`（小数2桁）で判定し、90.00ちょうどは完了に含みます。
率が未計測（`null`）の都市は、wikiで完了でない限り完了に数えません。

`/summary`の`cities_done`と`cities_osm_done`は、`boundary_geom IS NOT NULL`の都市だけを数える今の条件を引き継ぎます。

## 週次の集計（`ingest/compute_stats.py`と`sql/schema.sql`）

`dash_progress_history`に`cities_done INTEGER`の列を足し、毎週の記録に新しい定義の完了の数を入れます。
既存の`cities_osm_done`の列は、今と同じくwikiの完了の数を入れ続けます。
過去の週の行の`cities_done`は`null`のままにします。

列は`sql/schema.sql`に`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`で足し、今の冪等な書き方に合わせます。
集計のログの1行（`cities total=... in_db=... osm_done=...`）にも、新しい完了の数を足します。

## 境目の値

90という値は、APIと集計の2か所で使います。
2つのファイルは本番で別々の場所に置かれるため、共通のファイルにはまとめず、それぞれに定数を置きます。
2つの定数が一致することを、テストで確かめます（この置き方は設計者の判断です）。
画面は定数を持たず、`/summary`の`rate_done_threshold`を使います。

## 画面（`frontend/app.js`、`frontend/index.html`、`frontend/style.css`）

### 完了都市数のカード

見出しは「OSMインポート完了都市数」にし、「(wiki)」を外します。
大きな数字は`cities_done / cities_total`、割合も`cities_done`から計算します。
内訳は「うちwikiに完了と記載N都市」の1行だけにします（Nは`cities_osm_done`）。
今の「＋ ほぼ完了（率≥90%）: N 都市」の行は消します。
カードの下の説明文は「OSM wikiで完了と記載された都市と、取り込み率が90%以上の都市の合計です。」とし、90の部分は`rate_done_threshold`から入れます。

### 地域ごとのカード

「インポート完了N都市」のNを、`/regions`の新しい`cities_done`にします。

### 都市の一覧

「インポート作業」の列の印を、次の4種類にします。

| 条件 | 印 |
|---|---|
| `done_source`が`"wiki"` | 完了（wiki）。検証済みなら今と同じく「✓検証」を添える |
| `done_source`が`"rate"` | 完了（率） |
| 上のどちらでもなく、wikiで作業中 | 作業中 |
| それ以外 | 未着手 |

完了（wiki）と完了（率）は、同じ完了の色にします。
wikiで作業中の都市でも、率が90%以上なら完了（率）と出します（設計者の判断です）。
率の列の横にある「ほぼ完了」の印は消します。
列の見出しの補足「OSM wikiの記録」は「OSM wikiの記録と取り込み率」にします。
この列で並べ替えたときは、完了（wiki）、完了（率）、作業中、未着手の順に並べます（設計者の判断です）。

### 一覧の絞り込み

今の「インポート完了（wiki）」と「ほぼ完了（率≥90%）」を、次の3つに置き換えます（設計者の判断です）。

- 完了（すべて）
- 完了（wiki）
- 完了（率）

### 都市の詳細の欄

「OSMインポート(wiki)」の行は「インポート作業」とし、一覧と同じ印を出します。
完了（wiki）のときは、今と同じくwikiの完了日を添えます。
率の横の「ほぼ完了」の印は消します。

### 用語の説明の表

「OSMインポート完了都市数（OSM wiki）」の行を、新しい定義の説明に書き換えます。
wikiの`imports_list`へのリンクと、wikiで進捗を管理しているという説明は残します。
「ほぼ完了（率ベース）」の行は「完了（率）」に改め、wikiに記載がなくても率が90%以上なら完了に数えること、率が下がれば外れることを書きます。
率が100%に届かない理由の注記は残します。

「ほぼ完了」という言葉は、画面から無くなります。

## 手元で動かすための模擬データ（`frontend/gen_mock_data.py`、`frontend/data.js`）

模擬データを作るSQLを、APIの新しい応答の形に合わせます。
`data.js`は作り直します。

## テスト

次のことを確かめるテストを足すか、直します。

- `/summary`の`cities_done`が、wikiの完了と率90%以上の和集合の数になる。
  wikiで完了かつ率90%未満の都市、wikiでは完了でなく率90%以上の都市、両方の都市、どちらでもない都市を混ぜる。
- 率が90.00ちょうどの都市は完了、89.99は完了でない。
- 率が未計測の都市は、wikiで完了でない限り完了でない。
- `/regions`の`cities_done`と`cities_osm_done`が、地域ごとに上と同じ数え方になる。
- `/cities`の`done_source`が、4つの組み合わせで正しい値になる。
- `/summary`が`rate_done_threshold`を返す。
- 週次の記録の`cities_done`に新しい定義の数が入り、`cities_osm_done`はwikiの完了の数のまま。
- APIと集計の境目の定数が一致する。

## 文書

- `docs/DESIGN.md`の3.3節と9節に、この変更で取り決めを改めたことと、新しい完了の定義を書きます。
- `docs/UI_DESIGN.md`の補助の指標の表と、APIの表を、新しい名前に合わせます。
- `sql/schema.sql`の`cities_osm_done`の説明はそのままにし、`cities_done`の説明を足します。

## 本番への反映の順番

1. 本番のデータベースに`sql/schema.sql`を流し、列を足します。
2. APIのファイルを本番の置き場所に置き直し、APIを再起動します。
   再起動はsudoが要るので、利用者に依頼します。
3. 画面のファイルを、作り直した`data.js`と一緒に置き換えます。
   置き換える前に、`frontend/stamp_cache.py`で読み込みの版の印を更新します。
   画面はAPIの新しい名前を読むので、APIより先に置き換えないでください。
   APIが読めないときに画面が使う`data.js`も新しい形なので、画面に古い形への備えは要りません。
4. 次の週次の集計のあとで、記録に`cities_done`が入ったことを確かめます。

週次の集計は日曜01:00に始まり、3時間ほどかかります。
この時間帯に1から3を行わないでください。
